# AgentTeam 需求与技术设计文档

## 1. 项目背景与目标
AgentTeam 旨在构建一个多智能体（Multi-Agent）协作框架，实现任务分配、隔离开发与安全管控。系统包含一个作为指挥核心的 Lead Agent 和多个作为执行者的 Teammate Agent。通过消息总线通信、细粒度的原子任务流转、Git 工作树（Worktree）隔离以及破坏性操作闸门拦截，保证团队 Agent 在并发协作时的安全性、一致性与独立性。

## 2. 核心角色与职责 (Lead与Teammate)
系统通过角色分离确保管理权与执行权的解耦。

### 2.1 Lead Agent (主管)
Lead Agent 承担系统的大脑与任务调度职责：
- **事件驱动循环**：通过一个事件循环运行，负责监听用户的直接输入。
- **消息总线交互**：在收信箱（`Bus.peek(lead)`）中接收来自 Teammate 的消息。每次接收到消息后，会将其添加进历史记录（`history`）列表中，并重新请求一次大模型。
- **管理职能**：负责创建隔离环境、下发任务以及审批队友提交的执行计划。

### 2.2 Teammate Agent (队友)
每个 Teammate 被封装在 `TeammateRuntime` 类中，严格运行在一个单独的线程上，确保并发执行。其生命周期在以下两种状态中流转：
- **WORK (工作状态)**：不断请求大模型并执行工具。当大模型回复的这段话中不包含工具调用时，则退出大模型循环，并通过 MessageBus 发送 Lead 消息（汇报结果 + 空闲通知），随后转入 IDLE 状态。
- **IDLE (空闲状态)**：进入一个 while 循环。在此状态下优先监听并处理总线（bus）中针对自身的阻塞消息；当没有消息时，则主动去共享任务板（Task System）上获取并抢占任务。抢到任务后，回归到 WORK 状态。

## 3. 消息总线 (MessageBus)
消息总线是各 Agent 之间唯一且解耦的通信桥梁。

- **独立存储**：每个 Agent 都有一个专属的 JSON 文件作为其消息信箱。
- **并发安全写入**：写入消息时必须配加锁，防止多线程竞争导致 JSON 文件损坏。完成后调用唤醒函数通知处于阻塞状态的目标接收者。
- **数据结构约定**：JSON 文件的格式至少包含以下关键字段：
  - `from`: 发送方标识
  - `to`: 接收方标识
  - `type`: 消息类型（如通知、协议审批等）
  - `request_id`: 用于请求追踪和防止重复的唯一标识
  - `worktree`: 关联的工作树环境
  - `content`: 具体的消息内容或负载
- **破坏性读取**：采取 `read_inbox` 的破坏性方式进行读取，确保数据读取完毕后立即从信箱中销毁，避免出现消息的重复执行。

## 4. 任务系统与原子认领 (Task System)
采用文件系统支持的原子任务板来解决多队友之间的任务调度和依赖关系。

- **存储结构与依赖图**：所有的任务以单独的 JSON 文件存储在 `.task/` 目录下（例如 `task_xxx.json`）。文件内容包含：
  - `status`: 当前任务状态（限定为枚举值：`pending`、`in_progress`、`completed`）。
  - `owner`: 认领该任务的 Agent 标识。
  - `blockedBy`: 任务依赖前置图（包含被阻塞的前置任务ID列表）。
- **跨进程原子性**：在执行认领任务（更改状态及 owner）的操作时，代码会在整个目录或该文件级别进行加锁，以保证跨进程/多线程访问的安全性。
- **抢占逻辑**：Teammate 在获取到锁并读取任务 JSON 时必须确保满足两个条件：`status == pending` 且前置依赖 `blockedBy` 列表中的所有任务状态都已变为 `completed`。只有两者同时满足才能成功抢占。

## 5. 隔离环境 (Worktree)
为防止多个 Agent 同时操作同一代码库导致冲突或污染，系统引入了环境隔离。

- **创建与分配**：由 Lead Agent 负责创建。底层通过 `git worktree` 构建 Git 级别的工作树进行目录隔离。创建成功后，将工作树的名字（路径或标识）写入对应任务的 `worktree` 字段中。
- **动态环境映射**：代码全局维护了一个 `teammate_assignments` 字典，记录 `AgentName -> 工作目录` 的映射关系。当 Teammate 认领工作时，会自动更新并绑定该字典。
- **工具拦截执行**：Teammate 侧使用的 `bash`, `read_file`, `write_file`, `edit_file`, `glob` 等底层工具全部被拦截并包装过。在执行时，包装器会从分配映射中获取当前 Agent 的专属工作目录，将其作为工具操作的基准目录（CWD）。如果当前 Teammate 没有绑定工作树，则默认在仓库的主目录下执行。

## 6. 控制协议与闸门 (Control Protocol & Gates)
为防止大模型失控造成不可逆的破坏，系统在底层强加了行为审批和闸门控制。

- **协议包与去重**：控制协议通常用于系统级的“审批”和“关机”。消息包内携带 `request_id` 和协议类型。系统全局维护了一个字典来管理待回复的请求，防止对同一指令的重复回复。对于 Lead 拒绝 Teammate 计划的场景，将通过消息总线发送拒绝消息，使得 Teammate 能够接收并重新请求大模型进行修正。
- **全局状态闸门 (Plan Gates)**：全局维护了一个 `plan_gates` 字典，记录各个队友的权限状态（状态值为：`required`, `pending`, `approved`, `not_required`）。
- **强制拦截逻辑**：
  模型发起工具调用时，必须经过 `run_teammate_tool` 拦截函数。该函数内部存有硬编码判定：
  - 如果模型试图调用的工具名为 `bash`, `write_file`, `edit_file` （即具有破坏性的代码修改工具）；
  - 并且当前队友在 `plan_gates` 中的状态不是 `approved` 或 `not_required`；
  - 函数就会直接拦截执行，并返回一个错误信息注入给该队友模型的上下文，强迫模型调用 `submit_plan` 工具提交执行计划。
  - 该拦截状态将一直持续，直到 Lead 通过控制协议审批通过，并改变了该队友的 gate 状态，该工具才能被真正执行。

## 7. 异常处理机制 (Exception Handling)
- **并发防冲突**：对 MessageBus 信箱和 `.task/` 任务目录的读写均辅以严格的锁机制，保证并发环境下的数据一致性。
- **状态回归**：对于任务节点未设计 `failed` 状态。执行过程的容错与状态回归主要依赖于 Teammate 与 Lead 的沟通（通过 MessageBus 报告错误）以及重试机制。
