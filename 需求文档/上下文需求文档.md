# 上下文压缩模块需求文档

## 1. 目标与背景
为了确保大语言模型（LLM）的上下文不会超出最大 Token/字符 限制，并降低长上下文带来的成本，需要实现一套多级上下文压缩机制。该机制通过对工具输出、历史对话进行阶段性裁剪和总结，来维持上下文的健康状态。

## 2. 核心压缩策略

### 2.1 策略一：工具结果截断 (Tool Result Truncation)
- **场景**：用于工具调用返回大量文本时。
- **行为**：将工具调用的完整结果保存到本地（随机生成的文件夹/文件）。在上下文中，仅保留 `本地文件路径 + 结果的前 N 个字节`（如 2000 字节）。
- **条件**：需判断所有消息的总上下文大小是否达上限，以及单个工具调用结果是否超过单次上限。

### 2.2 策略二：对话滑动窗口 (Max Conversation Windowing)
- **场景**：当上下文消息总数达到指定上限（条数）时触发。
- **行为**：保留对话的“头部”和“尾部”，将中间部分裁剪掉。上下文中呈现为 `前 X 条上下文 + [被裁剪的消息数量及本地存档地址] + 最新 Y 条上下文`。
- **副作用**：每次触发时，需要将当前完整的总上下文归档保存到一个本地文件中。

### 2.3 策略三：动态水位回退 (Dynamic Context Eviction)
- **场景**：临时性压缩，当系统发现总上下文仍然面临超限风险时触发。
- **行为**：对历史上下文中尚未被截断的工具结果，追溯使用**策略一**的方法进行截断替换，直到总上下文长度降至总上限的 **80%** 以下。

### 2.4 策略四：LLM 智能总结 (LLM Semantic Summarization)
- **场景**：当执行完策略三后，总上下文依然超限；或者通过 `compact` 工具显式触发。
- **行为**：交给 LLM 对对话进行总结压缩。必须客观保留：**当前目标、剩余步骤、相关发现等**。
- **格式**：重组后的上下文格式为 `Compact 标记信息 + 用户原始输入 + 新的 LLM 对整段代码智能体对话的总结 + 当前上下文的地址`（发送给 LLM 进行总结前，需先将当前完整上下文保存到本地文件）。

## 3. 触发机制与工作流

### 3.1 `prepare` 预处理流程
在每次准备向 LLM 发送消息前，必须调用 `prepare` 函数依次判断并执行压缩类型：
1. **常规执行**：每次都会依次执行 **策略一** 和 **策略二**。
2. **条件执行**：若容量依然紧张，依次触发 **策略三** 和 **策略四**。

### 3.2 显式触发 (`compact` 工具)
- 系统提供一个 `compact` 工具供 Agent 调用。
- **机制**：在 `agent_loop` 这一层通过一个 bool 变量进行判断。调用该工具仅仅是作为一个标记。
- **执行时机**：因为需要等待当前轮次结束、所有工具调用结果都返回后，此时的压缩才具有实际意义。在轮次结束后判断该 bool 标记，若为 `true` 则直接触发 **策略四**。

## 4. 错误恢复机制
- **场景**：当请求 LLM 时返回上下文过长（Too long）的错误。
- **机制**：
  1. 通过一个变量判断当前剩余的**可恢复次数**。
  2. 触发紧急恢复，恢复方式与 **策略四（LLM 智能总结）** 相同。
  3. **特殊要求**：在此紧急恢复过程中，必须完整保留**最近的 5 条消息**不参与压缩总结。

## 5. 常量与配置定义
代码中需要通过常量明确表示以下配置：
- `MAX_TOTAL_CONTEXT_SIZE`: 总上下文大小上限
- `TOOL_RESULT_PREVIEW_LENGTH`: 单个工具调用结果保留的前缀字节数（如 2000）
- `MAX_MESSAGE_COUNT`: 触发策略二的最大消息条数
- `HEAD_RETAIN_COUNT`: 策略二中保留的头部消息条数
- `TAIL_RETAIN_COUNT`: 策略二中保留的最新尾部消息条数
- `SAFE_CONTEXT_RATIO`: 策略三的回退安全水位比例（0.8）
- `RECOVERY_RETAIN_COUNT`: 错误恢复时强制保留的最新消息条数（5）

## 6. 实现规范
1. 所有需求逻辑统一写在一个 `Compression`（压缩）类中。
2. 可复用的逻辑（如保存文件、计算长度）尽量封装为独立函数。
3. 对每种的上下文上限及相关配置都通过一个常量来进行表示。
